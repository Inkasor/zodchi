# Безопасность

[English](../../SECURITY.md) · [Русский](SECURITY.md)

Zodchi пока выпускается как бета-версия. Не передавайте в отчётах ключи API, файлы авторизации, базы данных, содержимое частных проектов и полные ответы моделей.

## Как сообщить об уязвимости

Используйте приватный отчёт об уязвимости в разделе Security публичного репозитория. Если он временно недоступен, свяжитесь с автором через профиль GitHub, не публикуя технические подробности в открытой задаче.

В сообщении укажите версию Zodchi, операционную систему, затронутый модуль, способ воспроизведения и возможное влияние. Секреты замените безопасными примерами.

## Провенанс релиза

Доверие к опубликованному релизу устроено в два слоя, и это разные проверки.

- Релизный workflow проверяет криптографически. `gh attestation verify` сверяет Sigstore-бандл скачанного архива с этим репозиторием, с подписавшим его релизным workflow и с точным исходным коммитом из релизного манифеста. Это выполняется на Windows, macOS и Linux до того, как релиз выходит из состояния draft, и повторяется против уже публичного релиза.
- Установщик первой загрузки проверяет по атрибуции. Пока на машине ещё нет кода Zodchi, `install-latest` требует, чтобы все ассеты загрузил `github-actions[bot]`, чтобы архив совпадал и с файлом контрольных сумм, и с релизным манифестом, чтобы указанный в манифесте workflow run завершился успешно на указанном коммите и чтобы GitHub по-прежнему хранил provenance-запись для точного дайджеста этого архива. Эту запись он читает через GitHub API по TLS; сам Sigstore-бандл он не разбирает, потому что первая установка не вправе рассчитывать на наличие GitHub CLI.

Однострочный bootstrap скачивает `install-latest.mjs` из основной ветки этого репозитория по TLS, поэтому самая первая загрузка держится только на подлинности GitHub; всё остальное выше сверяется с релизным манифестом и attestation. То есть установщик доверяет хранилищу attestation в GitHub, а не выводит подпись заново. Криптографический вывод — работа релизного workflow, а релиз, который её не прошёл, из draft не выходит.

## Границы

- Поставка не должна содержать личные базы, ключи, файлы авторизации и абсолютные пользовательские пути.
- Секреты для совместимых API передаются только через переменные окружения.
- Обычные сообщения неактивной сессии не перехватываются. `/zodchi` включает принадлежащий установке условный router только для точной пары client/session; в остальных чатах он ничего не делает и запрещает скрытую смену проекта. Установщик не перезаписывает одноимённый чужой skill, не удаляет изменённое управляемое содержимое и не перехватывает hooks или команды другой установки. Устаревший alias `/zod` снимается только неизменённым и принадлежащим этой установке.
- Постоянные квитанции Gateway содержат расход, хеши, время, статус, компактные ошибки и ссылки на артефакты, но не полные промпты, ответы, транскрипты и тела исходников. Политика приватности конкретного проекта может дополнительно сузить хранение.
- Пишущие шаги объявляют канонические ресурсы и в фиксированном порядке получают shared/exclusive leases. Ресурс с недоказанной идентичностью получает статус `unavailable`, а не глобальную блокировку проекта или незащищённую запись.
- Внешние исполнители обмениваются подписанными, привязанными к хешам request/result packets. Разрешение необратимого действия связано с objective, plan, checkpoint и точным состоянием действия; изменение любого входа делает разрешение недействительным.
- Публикация, развёртывание, изменение доступов, живых данных и другие необратимые действия требуют отдельного решения владельца. Зелёный gate, reviewer PASS или запись `OWNER_READ` его не заменяют.
