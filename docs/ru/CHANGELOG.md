## 0.6.12 — 2026-09-02

- Workflow run связывается с точными `(client, session_id)` при приёме сообщения, поэтому два чата Zodchi одного проекта больше не смешивают историю и ожидающие уточнения.
- Классификатор теперь создаёт и сохраняет самостоятельный resolved objective. Research, планирование, исполнение и возобновление получают разрешённый смысл, а не зависимую от контекста реплику вроде «все три».
- Read-only исследование теперь работает с зарегистрированным инвентарём исходников проекта, а не принимает контролируемые документы за весь репозиторий. Завершённый ответ обязан назвать просмотренные пути; WorkflowPlatform проверяет их внутри зарегистрированных корней и сохраняет границу исследования как доказательство прогона. Строгая схема ответа использует только поддерживаемые провайдером ключи JSON Schema, а failed receipt исследователя сохраняет категорию ошибки провайдера вместо ложного сообщения о невалидном JSON модели.
- У прямого research теперь три разных исхода: подтверждённый источниками `answered` завершает run, валидный `insufficient` сохраняется и блокирует run без ложного успеха, а ошибка провайдера или транспорта завершает run как `failed` со своей технической категорией.
- WorkflowPlatform теперь сама собирает для прямого research ограниченный пакет релевантных исходников внутри зарегистрированных корней и source scope. Исследователь получает выбранные фрагменты и метаданные полноты вместо зависимости от shell-доступа; ответ `answered` может ссылаться только на реально переданное содержимое, а ссылка на путь только из инвентаря завершается fail-closed.
- Программное исследование теперь отделяет контролируемые документы от доказательств реализации. Отбор исключает текстовые документы из пакета исходников, предпочитает пути, связанные с явными идентификаторами проекта, и требует хотя бы один реально переданный исходник для результата `answered`; dry-run откладывает чтение содержимого до исполнения.
- Research по прозаической формулировке теперь извлекает межъязыковые технические термины из строк проекта, содержащих предмет вопроса, и ставит редкие совпадения в именах исходников выше общих символов. Source evidence обязательно для всех дисциплин каталога, способных делать выводы о реализации, а не только для software и 1С.
- Межъязыковой термин теперь участвует в обычной оценке релевантности, а не перекрывает её; один соседний ряд документа может дать ограниченный терминологический мост, а generated/build-каталоги больше не конкурируют с исходниками реализации. При равной релевантности обычные каталоги реализации идут раньше тестов, миграций и scripts, не исключая их из поиска.
- Ранжирование исходников по прозаическому вопросу теперь сохраняет более широкий ограниченный словарь корпуса, объединяет варианты регистра и считает доказательством пути только совпадение нескольких терминов в имени файла. Регрессия на реальном репозитории проверяет внешние операции, передачу исходников исследователю и состояние недостаточного research, а не только идеальные фикстуры.
- Production research и его регрессия на реальном корпусе используют один экспортируемый контракт расширения, числа кандидатов и финального отбора, поэтому тест больше не может незаметно работать с другими лимитами, чем живой intake.
- Общий контракт research-ranking сохраняет до ранжирования сорок найденных в самом корпусе идентификаторов, поэтому редкие составные имена реализации не вытесняются при росте обычной документации и readiness-кода; число читаемых и возвращаемых файлов при этом не расширяется.
- Клиентские hooks и session-router теперь семантически слепы: каждое обычное сообщение без изменений получает классификатор. Подтверждение профиля стало типизированным ожиданием текущего чата, поэтому согласие, отказ, вопрос и новая задача определяются по зарегистрированным вариантам и истории, а не по ключевым словам или регулярным выражениям транспорта.
- Промпт и валидатор planner теперь одинаково описывают пути артефактов. Read-only выводы остаются структурированными доказательствами, а одна ограниченная попытка schema-repair исправляет неверный ответ planner до падения run.
- Семантический контекст теперь fail-closed: безсессионные CLI-, evidence- и фоновые прогоны явно stateless и не читают общую историю проекта или ожидающие ответы из чатов.
- При обновлении живое ожидание старого чата, которое нельзя доказуемо привязать к одной сессии, отменяется с миграционным событием, а не остаётся невидимым pending-запросом. После обновления такой запрос нужно повторить в его чате.
- Вход из Cursor подготовлен как preview через его штатные session hooks и закрепляемый Custom Mode `/zodchi`. Обычные чаты Cursor не перехватываются, доставка связывается с точными conversation/generation ID, а неоднозначный multiroot завершается fail-closed.
- Две управляемые копии skill Zodchi стали host-neutral: Cursor может использовать любое из совместимых глобальных расположений без третьей конфликтующей slash-команды.
- В AgentGateway добавлен preview-провайдер OpenRouter: ключ только из окружения, строгий JSON Schema routing, нормализованные token/cache/cost-метрики и обязательный live smoke до назначения роли.
- Cursor и OpenRouter остаются preview-возможностями. На конкретной установке каждая из них недоступна до собственного live smoke; их отсутствие на машине владельца релиза не блокирует стабильный выпуск.
- Требования роли к записи теперь fail-closed проверяются на границе AgentGateway. Каждый вызов обязан объявить, разрешает ли активный контракт запись; несовместимая возможность профиля или отсутствие требования отклоняются до запуска провайдера.
- Граница записи теперь входит в явный контракт возможностей исполнителя: переданный контекст, чтение и поиск по проекту, языковые сервисы, процессы и долгоживущие процессы, запись, сеть, автоматизация браузера, захват экрана, MCP и skills. Gateway выводит для каждого локального профиля статус, силу ограничения и способ доступа с учётом провайдера; декларативная или неизвестная гарантия не удовлетворяет техническому требованию роли.
- Worker браузерных Web- и Web-game-пакетов может изменить код и сразу посмотреть результат через явно разрешённый Codex-плагин Browser или Chrome вместе с `node_repl`. Браузер и захват экрана остаются необязательным усилением: их отсутствие не блокирует implementation, fix, testing и verification; детерминированный browser gate и приёмка владельца остаются отдельными авторитетами.
- Поддержка external runtime больше не выдаёт worker общий `exec_command`: команды проекта и browser proof выполняются зарегистрированными детерминированными проверками платформы, а роли incident, backup/restore и activity operations сохраняют запуск команд там, где этого требует контракт.
- Поле `capabilities` в сгенерированном профиле пакета теперь означает обязательные возможности исполнителя, а не прежний список allowed skills. Необязательные browser-возможности остаются в границах роли и не превращаются в условие readiness.
- Browser-capable worker может явно получить установленный Browser/Chrome-плагин и `node_repl`, но одна конфигурация остаётся `unknown`, а плагины интерактивного рабочего места не наследуются. Исправленный Windows-smoke импортировал актуальный `browser-client`, запустил его runtime внутри дочернего CLI и зафиксировал отсутствие подключённого Browser/extension backend в этом прогоне; это динамическое отсутствие backend, а не потерянный Gateway allowlist или API. Захват экрана запрещается там, где это явно требует контракт роли; технического запрета долгоживущих процессов пока нет до появления обеспечиваемой провайдером границы.
- Smoke браузерной возможности больше не требует заранее возможность, которую пытается доказать. Он поднимает одноразовую локальную HTTP-страницу с неизвестными модели значениями, допускает только обычный writable-контур worker и подтверждает browser automation лишь тогда, когда платформа независимо наблюдает browser navigation, загрузку подресурсов и исполнение JavaScript вместе с точными значениями страницы и allowlisted-компонентами receipt. Самоотчёт модели о screenshot остаётся `unknown`, пока внешний контур не вернёт проверяемый артефакт захвата.
- Отчёты browser smoke версионируются и явно ограничивают силу доказательства: sentinel-последовательность защищает от случайного ложного успеха, но может быть намеренно воспроизведена; общий browser status следует наблюдению платформы и не зависит от самоотчёта о screenshot. Сохранённое evidence schema v1 подтверждает только недоступный backend в том историческом прогоне.
- Провайдер-независимый browser-контур теперь может назвать один локально зарегистрированный Playwright-совместимый MCP-сервер через `browserMcpServer`. Codex и OpenCode переносят только разрешённые native-регистрации, а Claude получает выбранные определения через временный `--mcp-config --strict-mcp-config`. Отсутствующий сервер останавливает вызов до работы модели, Kimi и Cursor не могут объявить этот контур, а browser/capture остаются `unknown` до прохождения своих независимых evidence-требований.
- У зарегистрированного MCP-контура появился провайдер-независимый smoke: он проверяет фактический перенос сервера, наблюдает общий browser sentinel и при успешном capture записывает размер и SHA-256 сохранённого PNG. Отчёт явно предупреждает, что writable-модель может намеренно воспроизвести или подделать эти сигналы, поэтому project gates и owner acceptance остаются независимыми.
- MCP-smoke распознаёт как прямой структурированный результат, так и актуальную result-обёртку Claude CLI и fenced JSON, поэтому технически наблюдавшийся sentinel больше не превращается в `inconclusive` только из-за транспортной упаковки того же ограниченного payload.
- Вызовы Claude теперь передают зарегистрированную схему роли через штатное значение CLI `--json-schema`, а MCP-smoke может сохранить screenshot по явному пути доказательства внутри проекта. Так результат модели остаётся машинно читаемым, а allowed-root граница Playwright позволяет получить проверяемый артефакт без доступа к системному temp.
- Сохраняемое MCP-evidence заменяет локальные пути проекта и временных каталогов в структурированном объяснении провайдера переносимыми маркерами, а сам артефакт записывается с относительным путём проекта и digest.
- Квитанция Claude теперь честно описывает среду как `mcp-config-only`, а не как эфемерный home: изолируется только строгая MCP-конфигурация, но не фоновые настройки, hooks и skills Claude. Несовпадение регистрации browser MCP получает код profile/capability mismatch, а screenshot считается техническим доказательством только при наличии IHDR с viewport не меньше 800×600, а не по одной PNG-сигнатуре.
- Доказательство screen capture теперь декодирует сохранённый PNG и требует случайную матрицу sentinel 8×8 именно этого прогона: посторонняя картинка нужного размера больше не считается достаточной. Отчёт явно называет регистрацию MCP изолированной политикой пробы, не создавая впечатления установки в живую политику владельца; штатный `--json-schema` у Claude остаётся общим продуктовым контрактом провайдера, а не настройкой одного smoke.
- Профиль, в котором запрет записи держится только на инструкции модели, не становится молча подходящим роли, запрещающей запись. В локальном профиле теперь можно адресно зарегистрировать `acceptedDeclarativeBoundaries` для конкретной возможности и списка ролей с обязательной понятной владельцу причиной; исключение действует только для forbidden, но никогда для required. Readiness и квитанция показывают `accepted_declarative`, а любая не указанная роль по-прежнему завершается fail-closed.
- Runtime readiness вызывает Gateway-owned preflight тогда, когда известна проверяемая область: профили classifier и researcher проверяются до приёма, а после классификации до продуктивной работы проверяются только роли выбранного workflow на выбранном operational level. Несовместимый оператор выпуска или доступа больше не отключает посторонние маршруты. Диагностика установки и обновления вызывает ту же команду Gateway вместо собственной реализации слияния policy; отсутствующий `writes` по-прежнему означает отсутствие записи.
- Documentator стал read-only модельной ролью: он возвращает валидируемое предложение `documentator.v1`, а WorkflowPlatform сохраняет эксклюзивный worktree lease, атомарно применяет операцию, запускает Document Lint и откатывает неуспешное изменение.
- Операторы выпуска и доступа стали read-only модельными ролями предложения. Они могут выбрать только зарегистрированную `release_operation.v1` или `access_change.v1`; точное предложение и версия определения операции входят в hash подтверждения владельца, а модель не получает команды или право записи.
- Одобренные операции выпуска и доступа исполняются через подписанный external control plane. WorkflowPlatform атомарно отправляет зарегистрированную операцию, хранит в БД только хеши и аудиторские метаданные, принимает результат лишь от привязанного ключа executor и перед завершением заново запускает детерминированный gate.
- Завершённый внешний результат обязан назвать точную одобренную ревизию и среду выпуска либо субъект, ресурс и дельту прав. Расхождение отклоняется до записи результата, а проверка после операции запускает отдельно зарегистрированные проверки самой операции вместо повторения локального preflight; проверенный результат материализует доказательство выпуска или изменения доступа.
- Проверка после внешней операции сохраняет уже разрешённую область изменений и в исполнении, и в аудиторском контракте, а смысл payload разбирается только после проверки подписи. Release/access больше не получают предварительную цепочку evidence о ещё не выполненной операции, тогда как backup/restore сохраняет реальный flow от наблюдения до проверки здоровья.
- Две сохранённые Windows-пробы раздельно записывают самоотчёт модели о доступности нативного чтения и техническую ошибку провайдера/процесса. Вместе они показывают, что в этом read-only контуре модель не получила нативный reader, а оставшийся путь через локальный процесс запрещён политикой; ни одна проба отдельно не объявляется более сильным доказательством.
- Пробы возможностей Codex считают SHA-256 по полной сырой ошибке провайдера до ограничения отображаемого текста и отдельно фиксируют исходный размер и факт усечения сохранённого фрагмента.
- External executor и его release/access operations можно регистрировать и просматривать через CLI. В существующей установке нужно перевести затронутые профили операторов в read-only и зарегистрировать детерминированные операции; до этого недоступны только эти два маршрута, а остальные продолжают работать.
- Для установок с пользовательскими пакетами проверен путь обновления на 0.6.12: полная копия data root, миграции 035-036, генерация из настроенного definitions, повышение версии каждого изменившегося manifest и импорт каждого proposal только после явного подтверждения. Старое имя версии с новым содержимым по-прежнему fail-closed отклоняется как collision.
- В проверенной установке владельца три активных пакета переведены на prompt builder 3.2.0 и patch-версии `zodchi.product-development` 2.9.1, `shared-lore.canon` 2.9.1 и `shared-map-engine.core` 2.5.1. Профили documentator и операторов read-only; два исключения Kimi остаются видимыми как восемь назначений `accepted_declarative`, конфликтов профилей нет.
- Browser evidence из изолированной Claude-пробы Playwright не переносится в live policy без выбранной целевой роли и профиля.
- Маршруты release и access остаются явно недоступными до регистрации реальных подписанных `external operations`; отсутствие не выдаётся за пройденную возможность.
- Диагностика install/update распознаёт явный итог Gateway `accepted_declarative` и сохраняет его как `admission_status`, а не выдаёт принятое владельцем исключение за транспортную ошибку preflight.
- Диагностика возможностей install/update теперь учитывает включённые назначения профилей даже без активного контракта роли и больше не показывает владельцу усечённый результат по сравнению с runtime readiness.
- Прямые назначения classifier и researcher теперь допускаются к приёму сообщения только при наличии активных project-scoped контрактов. Финализация пакета добавляет оба контракта и их document bindings, если пакет их не объявил, а registry-backed вызов больше не обходит метаданные выбранного контракта.
- Контекст диалога классификатора теперь ограничивается `context_limit_bytes` активного контракта роли classifier; отдельные настройка и колонка workflow `history_budget_bytes` удалены. Переносимые workflow-пакеты переходят на schema v3 и prompt builder 3.3.0, поэтому пакеты schema v1/v2 перед импортом нужно перегенерировать и повысить их версию.
- Сохранённые Windows-пробы Kimi 0.40.1 показали, что workspace trust не ограничивает запись: при отсутствии trust-записи до и после обоих прогонов модель изменила запрошенный файл проекта штатными инструментами `Write` и `Edit`. Режим CLI `--plan` не может служить границей AgentGateway, потому что Kimi запрещает сочетать его с неинтерактивным контуром `--prompt`. Запрет записи у ревьюеров поэтому остаётся декларативным и сохраняет явно принятые владельцем исключения.
- AgentGateway теперь извлекает из структурированных событий провайдера только метаданные вызовов инструментов без аргументов до ограничения временного вывода. WorkflowPlatform перед приёмкой результата сверяет наблюдавшиеся классы `apply_patch` и `exec_command` с активным контрактом роли; расхождение закрывается отказом и остаётся видимым в квитанции, а ненаблюдаемый транспорт сохраняет статус `unavailable`, а не пустой успех. Preview-контур Cursor переведён на поток структурированных событий для будущего постфактум-аудита.

## 0.3.1 — 2026-08-25

- Проект может состоять из нескольких папок. Один корень остаётся основным и записываемым, остальные регистрируются явно, каждый со своим уровнем доступа. Работа, которая сводит две системы, должна читать и сторону отдачи, и сторону приёма, а ни одна из них не лежит внутри другой — до сих пор такой прогон видел половину того, о чём шла речь. Документ на корне только для чтения никогда не предлагается как записываемый, а запись в него отклоняется: правка чужих файлов относится к маршруту, проверкам и ревью того проекта, которому они принадлежат.
- Платформа собирает исходники, а не только зарегистрированные документы. Роль читает то, что для неё собрали, и сама файлы не открывает — именно это делает прогон воспроизводимым, а его стоимость ограниченной. Регистрация проекта уже зарегистрировала его папку, поэтому сбор охватывает то, что проектом считает сам git — отслеживаемые и неигнорируемые файлы, — а объявленный в маршруте `sources` это сужает, а не включает. Что является документом, по-прежнему решает регистрация: у незарегистрированного файла нет авторитета, его никто не пишет, и его текст в контекст не попадает. Имя, похожее на учётные данные или на дамп, отклоняется при любой области.
- Сбор ищет в проекте идентификаторы, которые уже есть в самом запросе, до любого обращения к модели. Перечень файлов говорит, что существует, но не говорит, где живёт предмет запроса, а в проекте из тысячи файлов выбор путей по именам — угадывание. Планировщик получает файлы, которые действительно упоминают спрошенное.
- В промпте роли сказано, что её контекст собран для неё. Роль с пустым списком инструментов делала вывод, что исходники недоступны, и просила владельца вставить их в сообщение, тогда как на самом деле их просто не собрали.
- Квитанция считает изменения по каждому записываемому корню. Учёт только основной папки оставил бы всё, что вызов сделал во второй, вне записи, которая и существует, чтобы сказать, что он изменил.

- Сбор читает проект на том языке, на котором проект написан. Запрос сформулирован обычными словами, код — идентификаторами, а перевод между ними лежит в самом проекте: в подписи, в комментарии, в тексте запроса. Сбор ищет слова запроса, снимает с найденных строк идентификаторы и ищет уже их. Ничего не угадывается и модель не участвует — каждое имя во втором проходе прочитано из этого проекта, то есть существует в нём. Слово берётся в работу, только если оно достаточно редкое, чтобы что-то значить, и это измеряется, а не задаётся списком.
- Одно сообщение закрывает все вопросы, на которые ответило. Платформа задаёт несколько вопросов сразу, человек отвечает на них одним абзацем; запись одного ответа и отмена остальных теряла то, что было сказано.
- Неверно названное уточнение больше не роняет прогон. Уточнение всё равно закрывается следующим сообщением, поэтому неизвестный идентификатор отбрасывается и записывается, тогда как раньше он проваливал классификацию и выбрасывал вместе с ней и ответ, и оплаченный вызов. Решение по действию остаётся строгим: оно что-то авторизует, и названное неверно остаётся открытым.
- При провале классификации сообщается, какой контракт нарушен, вместо ссылки на запрос или настройки проекта.
- Прогон, упавший на входе в исполнение, теперь завершается. Исполнение может упасть до того, как что-то запланировано — контракт роли не разрешает классифицированный тип работы, роли не назначен профиль на этом уровне, — а из состояния classified переход в отказ отсутствовал: человеку сообщалось об отклонении, тогда как сам прогон навсегда оставался classified, ни завершённым, ни ожидающим, и подобрать его было уже нечем. В ответе теперь называется нарушенный контракт.
- Проект на Codex без настройки доставляет подготовленный ответ, а не теряет его. Рекомендательный вывод передаётся через additional-context, и наблюдался ход Codex, не получивший ни этого контекста, ни подготовленного текста: классификация отработала, вызов оплачен, ответ не дошёл ни до кого. Для Codex умолчанием стала блокирующая форма, которую соблюдают оба хоста. Проект, где режим доставки задан, получает заданный режим.

- Зарегистрированный проектом тип работы принимается, даже если собственный запасной список платформы старше него. Пакет вправе регистрировать нужные его маршрутам типы, а прогон всё равно сверялся с замороженным списком — маршрут, который предлагали все каталоги, не мог начаться. Теперь источник истины — реестр, а список только запасной вариант для вызова без него.
- У воркфлоу, все шаги которого названы по проверкам, снова есть кому его исполнять. Исключение шагов с «тестовыми» именами не пускает работу фазы проверки в рабочие шаги, но на маршруте, который целиком из таких шагов, не оставляло ничего исполнимого.
- Требуемый документ, которому удовлетворяют несколько зарегистрированных, теперь сообщает, что воркфлоу нужен шаг планирования — он и решает выбор, — вместо доклада о неоднозначности без средства. Маршрут обновления документации этот шаг объявляет.
- Примерный пакет указывает свою версию сам, а не наследует общий умолчательный. Этот умолчательный проставляется и в контракты всех ролей во всех пакетах, поэтому его подъём ради одного примера молча переверсионировал их все.

<section id="0_3_0_beta_13_2026_08_25" status="working">

## 0.3.0-beta.13 — 2026-08-25

- Воркфлоу, объявивший свои шаги, исполняется как объявлено, без вызова планирования вообще. Его автор уже назвал роли, порядок, типы артефактов и проверки; просьба к модели придумать это заново и позволяла плану называть шаги, которых в маршруте нет. Объявленный шаг планирования по-прежнему выполняется: изменению нужны пути и цели, которые может дать только сообщение.
- Вывод плана не может породить разрешённый путь, а исполнитель без него не вправе менять ничего, поэтому воркфлоу, чьи рабочие роли умеют писать, обязан объявить шаг планирования. Это проверяется для каждого пакета, а маршрут изменения доступа получил недостающий шаг.
- У решения владельца три исхода, а не два. Человек, которого просят разрешить действие, может и не соглашаться, и не отказывать: сомневаться, переспрашивать, соглашаться отчасти. Продолжает ожидающий прогон только недвусмысленное «да», отказ его закрывает, всё остальное оставляет решение открытым и отвечает человеку. Прочитать сомнение как согласие значит совершить действие, которого никто не разрешал.
- Полученное одобрение продолжает тот прогон, который его запросил, а не начинает новый. Подтверждающее сообщение классифицируется как разговор, поэтому цель и классификацию даёт сам приостановленный прогон; раньше эти одобрения не разрешались ничем и каждое сообщение начинало всё заново.
- Роли, которые маршрут вправе исполнять после решения владельца, теперь известны. Назывались только шаги до решения, поэтому у полученного одобрения не оставалось ничего исполнимого.
- Незакрытое взаимодействие передаётся классификатору под своим настоящим видом — именно он отличает вопрос от решения о действии.

## 0.3.0-beta.12 — 2026-08-25

- Назначение роли теперь записывает, какое переносимое требование оно удовлетворяет. Пакет называет ключ требования, а онбординг создаёт локальный профиль, поэтому сравнение их на равенство оставляло большинство контрактов ролей незагружаемыми, и ни один проект вообще не мог выполнять структурированную работу.

Каждый прогон записывает решение, поэтому проект рос, пока не переставало помещаться ничего, и ломался тем вернее, чем больше им пользовались.
- Планирование — объявленный шаг воркфлоу, а не платформенная роль, существование которой предполагалось; воркфлоу, объявивший свою форму без шага планирования, теперь так и говорит вместо сообщения о пропавшей роли.

Его проверяли по списку, которого не показывали, поэтому он называл сам себя, поручал правку роли без права правки и тратил рабочие шаги на работу, которую уже делают фазы верификации и документирования.
- Пакет обязан объявить локальный профиль для каждого переносимого требования, разрешённого его ролям; теперь это проверяется для каждого пакета.
