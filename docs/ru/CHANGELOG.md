# История изменений Zodchi

[English](../../CHANGELOG.md) · [Русский](CHANGELOG.md)

## 0.3.0-beta.10 — 2026-08-25

- MarketplacesData проверяет, что релиз действительно доехал до продакшена. Прогон GitHub Actions для точного коммита, ревизия, которую отдаёт сервер, и здоровье работающей службы были объявлены, но недоступны; теперь они вызывают зарегистрированные скрипты проекта, поэтому алиас сервера, пути и точка здоровья остаются в проекте, а в пакете лежит только имя скрипта.
- Разбор производственного инцидента идёт на производственном качестве во всех рабочих процессах веб-проектов компании. Процесс называл себя производственным, но объявлял MVP: одна обязательная проверка и ни одного независимого ревьюера.
- MarketplacesData направляет живой сбор данных в отдельный рабочий процесс. Сбор тратит настоящие запросы к маркетплейсам, и откат их не возвращает, поэтому сначала идут измеренный сухой прогон и ревью, затем владелец утверждает точные идентификаторы конечных точек, и запускается только утверждённый список.
- Роль оператора сбора не может отправить запрос на изменение, расширить утверждённый список конечных точек или раскрыть учётные данные.
- Обратимое изменение данных теперь проверяется и по самой базе, а не только тестами и сборкой, общими с правкой кода.

## 0.3.0-beta.9 — 2026-08-24

- Рабочий процесс объявляет качество, под которое он сделан, и это объявление стало нижней границей: классификатор может поднять уровень запуска, но не опустить, потому что на низком уровне отпадают проверки, на которых процесс держится.
- Hook умеет отдавать готовый ответ как окончательный, а не как совещательный контекст. В режиме доставки `final` ход завершается и ответ показывается напрямую, поэтому чат не может повторить уже оплаченное исследование; по умолчанию остаётся `advisory`.
- Каждое уточнение закрывается следующим сообщением: то, на которое ответил классификатор, помечается принятым, остальные — устаревшими. Раньше уточнения копились, и следующий классификатор читал уже отвеченные вопросы как открытые.
- В промпте классификатора весь неизменный контракт стоит выше состояния запуска, и в контракте теперь сказано, что означает каждое поле ответа и как выбираются уровень планирования и режим качества. Провайдер может переиспользовать префикс, а одно и то же сообщение больше не получает разный уровень.
- Режим доставки выбирается для каждого проекта в команде hook, потому что hook устанавливается по проектам.
- Project Lore записывает карточку LORE-CHANGE в `docs/decisions` до решения владельца, поэтому кандидат, оставшийся открытым или оказавшийся противоречием, всё равно оставляет запись и не попадает в канон. Процесс изменения дополнительно спрашивает область кандидата и влияние на оба проекта, а владельческий гейт есть на каждом уровне.

## 0.3.0-beta.8 — 2026-08-24

- Статистика запуска сообщает точку входа, из которой пришёл запуск. Поле `harness` у вызова повторяло провайдера шлюза и читалось как клиент чата, из-за чего запуск из Claude Code показывался как Codex; вместо него у запуска есть `client`.

## 0.3.0-beta.7 — 2026-08-24

- Харнесс определяется по единственным полям, которые различаются в двух событиях: Codex называет ход и модель, Claude Code — сообщение. Идентификатор сессии, путь к стенограмме и режим доступа присылают оба, поэтому ход Codex больше не записывается как Claude Code.
- Hook сохраняет имена полей полученного события, поэтому отправивший харнесс определяется по одной истории запусков.
- Инструкция, возвращаемая харнессу, прямо сообщает, что ход уже завершён, и повторяется после результата: вывод hook в обоих харнессах — совещательный контекст, а чат, заново исследующий ответ, тратит деньги пользователя дважды.
- Квитанции классификатора и исследователя несут запуск, к которому относятся; раньше это записывали только шаги структурированной работы.

## 0.3.0-beta.6 — 2026-08-24

- Классификатору предлагаются только те типы работ, которые проект действительно маршрутизирует, плюс разговор и уточнение: узкий проект больше нельзя классифицировать в отсутствующий маршрут.
- Ответы в режиме разговора, уточнения и исследования больше не требуют зарегистрированного маршрута: они выдаются напрямую и не входят в рабочий процесс.
- Проверка, которую нельзя выполнить, больше не блокирует процесс: она отмечается как недоступная, а покрытие гейта считается по выполнимым обязательным проверкам, поэтому проект блокируется только тогда, когда его действительно нечем проверить.
- В пакеты 1С и операций компании добавлен выполнимый поиск секретов на уровнях прототипа и MVP: ни в одном из них не было ни одной работающей проверки.
- Project M, Project R, Shared Map Engine, Shared Lore и 1С получили точки входа, которые их роли уже поддерживали: исправления, документация и прогон проверок.
- Рабочие процессы компании направляют проверку и тестирование в отдельный прогон проверок с ревью вместо отсутствующего маршрута.
- Релиз и плейтест инди-проектов идут на производственном качестве, процесс прототипа — на прототипном, а шаг ревью в 1С стал обязательным.

## 0.3.0-beta.5 — 2026-08-24

- События Claude Code распознаются по идентификаторам, которые реально присылает харнесс, поэтому запуски из Claude Code записываются под своим клиентом, а не как Codex.
- Поставляемый шаблон настроек Claude Code использует exec-форму команды: пути Windows не теряются при запуске hook.

## 0.3.0-beta.4 — 2026-08-24

- Claude Code становится второй точкой входа наряду с Codex через один общий hook UserPromptSubmit.
- Точка входа переименована в hooks/user-prompt-submit.mjs; прежнее имя файла Codex сохранено для совместимости с установленными релизами.
- Результат hook теперь передаёт additionalContext на верхнем уровне вывода — именно там его читает Claude Code.
- Запуски рабочих процессов сохраняют клиента-источник, а идентификаторы сообщений Claude Code используются для защиты от повторной доставки.

## 0.3.0-beta.3 — 2026-08-24

- Добавлено определение языка диалога для hook, состояния рабочего процесса, промптов моделей, вопросов и итоговых ответов.
- Человекочитаемые документы теперь доступны на английском и русском; машинные семантические инструкции используют английский.
- Удалены дубли README, историй изменений и лицензий, оставшиеся от отдельных репозиториев компонентов.
- Сборщик и линтер поставки обновлены под единую структуру продукта.

## 0.3.0-beta.2 — 2026-08-24

- Добавлены английское и русское человеческие описания с простым началом работы по одной ссылке.
- Установка и обновление оформлены как инструкции для LLM; добавлена проверяемая загрузка последнего GitHub Release.
- Добавлен переносимый рабочий поток разработки самого Zodchi.
- Подготовлена единая схема проекта Codex: исходники как основная папка, установленная копия и локальные данные как вторичные папки.

## 0.3.0-beta.1 — 2026-08-24

- Первый публичный снимок под названием Zodchi.
- WorkflowPlatform и AgentGateway объединены в одном репозитории с разными обязанностями во время работы.
- Добавлены переносимые рабочие потоки, уровни качества, классификация, документирование и программные проверки.
- Личные базы, назначения моделей, проекты, ключи и история запусков отделены от поставки.
- Добавлены воспроизводимая сборка, проверка состава, контрольные суммы и безопасное обновление.

Полная экспериментальная история до публичного снимка сохранена только в локальных репозиториях автора.
