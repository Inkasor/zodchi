# Как помочь проекту

[English](../../CONTRIBUTING.md) · [Русский](CONTRIBUTING.md)

Спасибо за интерес к Zodchi. Проект открыт для исправлений, новых рабочих потоков, проверок, исполнительных сред и улучшений документации.

## Изменения кода

1. Создайте короткую ветку от `main`.
2. Не добавляйте базы, ключи, файлы авторизации, журналы запусков и данные частных проектов.
3. Перед изменением маршрутизации, workflow, доказательств или поставки прочитайте принятые границы в [Архитектуре](../ARCHITECTURE.md).
4. У пользовательского намерения должен быть один семантический владелец: хуки и роутеры сессии работают только с протоколом и идентичностью. Они передают обычный текст пользователя классификатору без изменений и не определяют подтверждение, отказ, продолжение или тип задачи по ключевым словам, регулярным выражениям или командам-сокращениям. Детерминированный код проверяет структурированный результат классификатора, а не заменяет его.
5. Выполните `npm test` из корня репозитория.
6. Машинные документы должны иметь один корень `<document>`, уникальные семантические ID, сбалансированные теги, актуальные версии и границы, а также не содержать приватных путей. Выполните `node scripts/validate-source.mjs`; корневой набор тестов тоже запускает этот semantic/documentator lint.
7. Для изменений пакетов выполните `npm --prefix WorkflowPlatform run packages:check`. Сгенерированные XML и публичный каталог должны точно соответствовать явно названным definitions.
8. Для изменений поставки соберите её командой `npm run release:build` и проверяйте собранный релиз, а не только исходный checkout.
9. В запросе на изменение простыми словами опишите проблему, решение и выполненные проверки.

## Рабочие потоки

Переносимые настройки экспортируются WorkflowPlatform в семантический XML. Сначала проверьте пакет линтером, затем приложите обезличенные сценарии и ожидаемые маршруты. Локальные пути, профили, названия моделей и секреты в пакет не входят.

## Релизы

Релиз публикует workflow по тегу и никто больше. Не выполняйте `gh release create` и не загружайте ассеты вручную: такие ассеты не являются артефактами сборки, а workflow затем падает, потому что релиз уже существует.

1. Влейте релизный коммит в `main` и убедитесь, что `product.json`, `package.json` и версии обоих компонентов совпадают.
2. Отправьте аннотированный тег `vX.Y.Z`. Если релиз с таким тегом уже есть, workflow отказывается публиковать с `RELEASE_PREEXISTED`.
3. Workflow выполняет тесты, собирает архив, пишет `SHA256SUMS.txt` и `zodchi-release-manifest.json`, создаёт OIDC/Sigstore provenance и загружает всё в draft-релиз.
4. Smoke-задачи на Windows, macOS и Linux скачивают именно draft-ассеты через GitHub Release API, криптографически проверяют attestation командой `gh attestation verify`, проверяют контрольную сумму и пофайловый манифест, устанавливают продукт и выполняют рабочий поток целиком через детерминированного провайдера.
5. Только после этих проверок workflow публикует draft: тег с prerelease-частью (`-rc.*` и аналогичные) становится prerelease, стабильный semver — обычным Latest-релизом. Затем трёхплатформенный smoke повторяется уже для публичного Release.
6. Если post-publication smoke красный, workflow возвращает Release в draft. Такой тег не является поддерживаемой версией. Исправьте причину и выпустите следующую версию; опубликованные ассеты руками не чинят.
