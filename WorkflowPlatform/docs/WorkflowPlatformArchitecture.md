# Как устроена Workflow Platform

## Коротко

Workflow Platform — это рабочий процесс вокруг одного пользовательского чата. Пользователь говорит обычным языком, а система программно собирает контекст, вызывает классификатор, выбирает маршрут и передаёт отдельные этапы через Agent Gateway.

```text
чат пользователя
  → Codex UserPromptSubmit hook
  → Workflow Platform
  → Context Builder
  → LLM-классификатор
  → выбранный маршрут
  → Agent Gateway
  → роли и модели
  → проверки
  → Documentator
  → простой ответ в чат
```

## Workflow Platform

Workflow Platform отвечает за смысл и порядок работы:

- собирает контекст проекта;
- читает реестр проектов, ролей и документов;
- классифицирует задачу через LLM;
- выбирает тип работы, дисциплину, уровень планирования и режим качества;
- задаёт необходимые вопросы;
- формирует контекст для ролей;
- запускает проверки;
- управляет документами через Documentator;
- хранит состояние и результаты workflow в своей базе.

## Discovery, классификация и контекст

Discovery программно читает только зарегистрированные проект, workflow, цели, этапы, проверки, документы, права ролей, активные решения, pending approvals и артефакты. Git status и короткая история читаются только когда это явно разрешено в `workflow.discovery_json`. Известные имена документов и папок не используются как скрытые defaults.

Classifier получает закрытые справочники из Workflow DB, зарегистрированные `workflow_routes`, компактный стабильный снимок проекта, принятые решения, pending interactions, последовательную историю в пределах байтового бюджета и текущее сообщение последним. Ответ обязан точно соответствовать JSON-контракту версии 1. Лишнее поле, неизвестное значение, несуществующий pending interaction, незарегистрированный маршрут или не-JSON приводят к `classification_failed`; planner, worker и другие производственные роли не запускаются.

Короткое подтверждение не распознаётся регулярным выражением. Оно классифицируется моделью вместе с ожидающими решениями и упорядоченной историей. Обычный разговор вызывает только classifier и возвращает простой ответ. Research вызывает только researcher с документами, разрешёнными этой роли. Если сведений недостаточно, человеку возвращаются короткие вопросы без внутренних ID, профилей и JSON.

## Надёжное исполнение

Каждое пользовательское событие с устойчивым `event id` принимается идемпотентно: повтор возвращает уже созданный run и не запускает роли второй раз. Маршрут хранится как последовательность `workflow_step`; отдельной дублирующей таблицы очереди нет.

Исполнитель атомарно получает один готовый шаг и lease с ограниченным сроком. В базе хранится только хеш lease-токена. Запуск шага создаёт отдельную attempt. Одновременно активен не более чем один lease на шаг, а следующий обязательный шаг того же run не становится готовым до подтверждения предыдущего. Независимые задачи могут исполняться параллельно в изолированных рабочих каталогах.

После потери процесса истёкший lease освобождается. Обратимый шаг получает ограниченную повторную attempt с последнего подтверждённого этапа. После исчерпания лимита он попадает в dead-letter. Необратимый шаг не повторяется автоматически и требует записанного подтверждения. Pause, resume, cancel, ручной retry и восстановление lease доступны через CLI:

```text
node src/cli.mjs queue-recover --db <workflow.sqlite>
node src/cli.mjs run-pause --db <workflow.sqlite> --run <run-id>
node src/cli.mjs run-resume --db <workflow.sqlite> --run <run-id>
node src/cli.mjs run-cancel --db <workflow.sqlite> --run <run-id>
node src/cli.mjs dead-letter-retry --db <workflow.sqlite> --dead-letter <id> [--approved]
```

Бюджеты могут быть заданы для проекта, задачи, workflow, роли и attempt. Резервирование выполняется транзакционно и идемпотентно до вызова провайдера; превышение любого настроенного лимита создаёт `budget_hard_stop` и блокирует запуск.

## Структурированный контракт исполнения

Для каждой роли в Workflow DB хранится версионированный переносимый контракт: назначение и границы, допустимые задачи и артефакты, права на документы, allowlist инструментов и навыков, обязательные проверки, переходы, допустимые профили, лимиты, схема результата и эскалация. Локальное назначение конкретного профиля и модели хранится отдельно и не попадает в переносимый контракт.

Контракт роли не дублируется по режимам качества. К нему программно добавляется один из четырёх универсальных контрактов из `contracts/quality-contracts.xml`:

- `prototype` — одна рисковая гипотеза, минимальный обратимый результат и обязательная настроенная статическая проверка; отдельный reviewer не вызывается;
- `mvp` — один полный пользовательский сценарий, все применимые проверки и специально созданные тесты; reviewer вызывается только при высоком риске, защищённой границе или после цикла исправления;
- `production` — все проверки MVP, точная сборка, развёртывание, проверка целевой среды, наблюдаемость и откат; независимый reviewer обязателен, необратимое действие требует записанного решения владельца;
- `security-audit` — только чтение, явная модель угроз, покрытие, находки и остаточный риск; отсутствие настроенной проверки считается `unavailable`, reviewer по безопасности обязателен, исправление запускается отдельным маршрутом.

Workflow Platform владеет общим числом вызовов, временем, циклами исправления, проверками и эскалацией. Agent Gateway получает один уже подготовленный вызов и не повторяет его самостоятельно. Если для программного артефакта не настроено ни одной применимой проверки, gate не может стать зелёным.

Planner возвращает только результат строгой схемы версии 1. Если до исполнения нужны ответы человека, run переходит в clarification и worker не запускается. В остальных случаях программа сохраняет нормализованный пакет; свободный текст ответа planner в worker не передаётся.

Worker получает разрешённые пути, входы, проверки, артефакты и критерии завершения. Его результат проверяется по схеме и allowlist путей и артефактов. После него Workflow Platform запускает только зарегистрированные для проекта, типа артефакта и operational level проверки. Наличие `package.json` или языка программирования само по себе не включает никакой команды.

Reviewer возвращает ровно `PASS`, `CHANGES_REQUESTED` или `REJECT`. Он запускается только по универсальному контракту качества и проектным условиям эскалации. Exit code провайдера не считается review-решением; `CHANGES_REQUESTED`, `REJECT` и любой обязательный непройденный gate блокируют завершение. `PASS` не подменяет программные gates и отдельную человеческую визуальную, игровую, продуктовую или бизнес-приёмку.

Documentator получает один зарегистрированный документ и patch строгой схемы. Перед записью проверяются authority, право роли, операция и точная версия содержимого. Patch сначала применяется к временному файлу в той же папке и проходит lint; затем файл заменяется атомарно. В документ и нормализованные поля базы записываются уровень качества, версия контракта, тип доказательства и статус решения. Зелёные технические проверки дают `verified`, но не повышают решение до `accepted` без записанного принятия владельцем. При конфликте или ошибке исходный файл остаётся неизменным, а обязательный run не может стать completed.

## Переносимые workflow-пакеты

Пакет версии 2 содержит назначение и версию, полные контракты ролей, логические требования к профилям без секретов и локальных идентификаторов моделей, граф шагов и переходов, контракт состояний, маршруты, вопросы человеку, входные и выходные схемы, проверки и их привязки, четыре уровня качества и их проектные ограничения, документы с владельцами и правами, версии шаблонов запросов и обезличенные тестовые сценарии.

Сущности связаны устойчивыми смысловыми ключами. При импорте Workflow Platform создаёт локальные технические ID и хранит явное сопоставление. Формат — узкий XML-конверт с каноническим JSON payload. Конверт разбирается посимвольно по ограниченной грамматике: DTD, декларации, неизвестные entities, произвольные теги и атрибуты запрещены; regex-разбор XML не используется.

Импорт всегда двухфазный. `workflow-import-propose` проверяет структуру, зависимости, коллизии и версии, строит diff и связывает proposal с hash нормализованного пакета, hash исходного файла и hash состояния целевого проекта. `workflow-import-apply` требует `confirmed-by` и отклоняет изменившийся пакет, изменившийся target, повреждённый proposal, downgrade и конфликт той же версии. Повтор уже активной идентичной версии возвращает `no_changes`.

```text
node src/cli.mjs workflow-export --db <workflow.sqlite> --project <project-id> --workflow <package-key> --out <package.xml>
node src/cli.mjs workflow-import-propose --db <workflow.sqlite> --project <project-id> --package <package.xml> --proposal <proposal.json>
node src/cli.mjs workflow-import-apply --db <workflow.sqlite> --project <project-id> --proposal <proposal.json> --confirmed-by <owner>
```

## Контролируемый опыт v1

Experience store принимает только структурированный результат, компактную error category, gate outcomes, подтверждённую человеком обратную связь и технические метрики. Полные prompt/output, stdout/stderr и transcript запрещены. Предложение может изменить только `role_contract`, `prompt_template`, `check` или `route`.

Перед применением предложение прогоняется на сохранённых обезличенных сценариях. Для текущего и предложенного варианта сохраняются только `passed`, quality score, оценка стоимости и длительность; пользователю показывается сравнение. Применение требует явного `confirmed-by`, проверяет неизменность активной base version и создаёт новую patch-версию пакета. Неподтверждённое, неоценённое или устаревшее предложение конфигурацию не меняет.

## Agent Gateway

Agent Gateway не решает, что делать с проектом. Он отвечает за технический вызов модели:

- провайдер;
- профиль;
- роль;
- модель;
- параметры запуска;
- квитанция вызова;
- токены, кэш, время и ошибка.

Одна задача Gateway — один вызов провайдера. Исправления, повторные этапы и эскалация принадлежат Workflow Platform.

Gateway можно заменить или расширить, не переписывая рабочие процессы.

## Роли

Роль — это устойчивый контракт работы, а не название модели. Например:

- `classifier` — определяет намерение и маршрут;
- `producer` — помогает определить цель и приоритет;
- `researcher` — разбирает переданный контекст;
- `planner` — создаёт bounded-план;
- `worker` — выполняет ограниченный пакет;
- `reviewer` — проверяет результат;
- `documentator` — создаёт и изменяет документы;
- `tester` — формирует и анализирует тестовые проверки.

Конкретная модель назначается профилем Gateway и может меняться без изменения роли.

Вызов Gateway получает уже сформированный пакет роли. Workflow Platform связывает техническую квитанцию с attempt, хешем входного контракта, хешем структурированного результата и, когда применимо, ссылкой на артефакт или решение. Полные prompt и model output в Gateway DB не хранятся.

## Документы и владельцы

Документы не зашиваются в коде workflow. Они регистрируются в Workflow DB. Для каждого документа задаются:

- проект;
- путь;
- тип;
- authority;
- владелец-роли;
- доступ на чтение;
- доступ на запись;
- приоритет и назначение.

Context Builder выбирает документы по роли. Documentator может писать только туда, где у роли есть право записи.

## Как настраивается рабочий поток

1. Зарегистрировать проект и его корень.
2. Заполнить справочники доменов, дисциплин, типов задач и режимов качества.
3. Зарегистрировать документы проекта.
4. Назначить владельцев документов и права ролей.
5. Описать маршрут: какие роли идут последовательно и какие проверки запускаются.
6. Настроить профили Gateway для ролей.
7. Подключить hook к чату.
8. Провести безопасный тест без изменения файлов.

Обычный пользователь не должен вручную заполнять эти поля: onboarding-модель собирает сведения, предлагает настройки и просит подтвердить только важные решения.

## Hook Codex

В проекте Codex создаётся `.codex/hooks.json` с событием `UserPromptSubmit`. Hook запускает:

```text
node <путь-к-WorkflowPlatform>\hooks\codex-user-prompt-submit.mjs
```

После изменения hook Codex может пометить его как недоверенный. В таком случае пользователь должен включить его в интерфейсе Codex. До этого сообщения будут приходить в чат, но Workflow Platform запускаться не будет.

Для защиты от повторной доставки hook должен передавать устойчивый идентификатор события (`event_id`, `eventId`, `id`, `message_id` или `turn_id`). Если клиент не предоставляет такой идентификатор, Workflow Platform не подменяет его хешем текста: одинаковые сообщения могут быть двумя намеренными пользовательскими действиями.

## Локальные данные

Код можно передавать другим людям. Базы данных, история запусков, квитанции, проекты и ключи должны оставаться локальными:

```text
WorkflowPlatformData\workflow.db
AgentGatewayData\gateway.sqlite
```

Каждый пользователь проходит собственный onboarding.
